# Sanad browser Google account and sync

The existing Firebase project `gen-lang-client-0248696268` remains the identity authority. `/auth/google` offers Google sign-in only, with email/profile scopes and no Gmail or Chrome Sync API access. A verified Google account may use a non-Gmail email address. Browser data is linked to the verified Firebase UID, never a client-supplied email.

Desktop starts the flow in the OS browser at `https://ip-murad.com/auth/google`. A local five-minute nonce and S256 PKCE verifier bind the two-minute, one-use callback code to the initiating browser. `sanad://auth-callback` carries only code/state. Code exchange atomically consumes the code and issues a scoped, revocable 30-day browser session. Firebase tokens never appear in the deep link. Desktop credentials require OS-protected encrypted storage. Login is blocked while a proxy is enabled because opening the external OS browser would bypass it; subsequent sync uses the normal Electron session networking stack.

The branded `/api/browser/account` Netlify endpoint proxies to the deployed Supabase `browser-sync` function. The function independently verifies Google-signed Firebase tokens, then authenticates scoped browser tokens. Tables have RLS enabled and no anon/authenticated grants. Service-only invoker functions perform atomic exchange and vault revision comparison. Apply `supabase/functions/browser-sync/schema.sql` once as migration `sanad_browser_google_sync_v1`; deploy index.ts and its three adjacent modules with verify_jwt=false, since custom Firebase/scoped verification is implemented inside the function. Never place a service key in clients.

Sync starts only after the user confirms bookmarks, supported settings and ordinary tabs; history is optional. Private tabs, authentication URLs, cookies, passwords, payment data and security/proxy settings are excluded. Strict search remains mandatory. Limits are 1,000 bookmarks, 200 recent history URLs and 32 tabs per device, with up to 16 device operation ledgers and a 1.8 MB document. Supported preferences are explicitly allowlisted. The server stores AES-256-GCM encrypted documents with account-bound associated data; the service manages account keys. This is **not end-to-end encryption**. Web sessions are stored in origin-scoped localStorage; desktop sessions use the existing OS-encrypted store. Sign-out revokes this device's token while retaining local browsing data.

Per-device sequence numbers make retries idempotent. Atomic compare-and-swap retries merge concurrent devices. Acknowledged deletes are not recreated by unchanged stale clients. Explicit first-time merge combines local and cloud favorites, with remote supported preferences taking priority. Tab sessions are restored once per startup; native remote tabs sleep until selected. Network errors retain queued changes.

Chrome import is local and opt-in: preview counts first, then choose categories. Bookmarks preserve folder metadata. History is queried from a disposable copy of SQLite and WAL; Chrome files are never changed. Only compatible preferences are mapped. Clear SNSS session formats 1/3 are supported. Modern format 5 is OS-encrypted and is not decrypted. For those sessions, the optional source-available Chrome export assistant requests selected optional permissions and saves a JSON file locally for native import. It sends nothing to a server and is not a Chrome Web Store publication. No Login Data/cookie/password extraction is performed. OS-browser-only APIs and Chrome cloud data cannot be imported by Google sign-in.

Validation: Node model/controller/service tests cover signed Google identities (including non-Gmail), PKCE and code replay, account isolation, actual AES-GCM envelopes, concurrent merges, deletion, retry, private mode and session restoration. Native tests read fixture Chrome data through the actual worker and verify original files stay unchanged. Windows GUI tests exercise the real native callback and UI against an in-process network fixture; these are not tests against a person's live Google account.
